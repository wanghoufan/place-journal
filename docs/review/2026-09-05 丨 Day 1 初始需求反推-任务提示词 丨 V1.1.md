# 项目反推任务：如果从零开始，我应该怎样一次性把需求讲清楚？

你现在的任务不是继续开发项目，也不是简单总结项目。

请你完整复盘当前项目，并站在“项目已经发展到今天这个状态”的终点，反向推导：

> 如果这个项目今天完全不存在，我重新从 0 开始开发，并且希望尽可能少返工、少走弯路，那么我在第一次和「计划者 / Planner」讨论项目时，应该给出一份怎样的完整提示词，才能让计划者尽可能在一开始就理解我真正想做的产品，并设计出接近当前成熟版本的方案？

---

# 一、你的角色

你是本次项目的：

**产品复盘分析师 + 需求反推专家。**

你的职责是：

1. 完整了解当前项目最终已经发展成什么样；
2. 研究需求是怎样一步步补充和变化的；
3. 找出哪些内容其实应该在项目第一天就明确；
4. 从当前成熟产品反向生成一份高质量的 Day 1 初始需求；
5. 最终形成一份可以长期保存、以后重复参考的 Markdown 文档。

你本轮：

- 不负责继续开发；
- 不修改业务代码；
- 不自行增加新功能；
- 不把重点放在代码质量审查；
- 不直接执行新的产品改造。

本轮只负责：

> **复盘 → 反推 → 沉淀。**

---

# 二、背景

我是编程小白。

我不会提前准确地说出：

- 应该使用什么技术；
- 数据库应该怎样设计；
- 页面应该怎样拆分；
- 状态应该怎样管理；
- API 应该怎样组织；
- 哪些需求属于前端、后端或数据库；
- 哪些东西现在不做以后会返工。

我通常只能描述：

- 我想解决什么问题；
- 我平时会怎么使用；
- 我希望界面大概是什么感觉；
- 我希望它做到什么事情；
- 哪些地方现在用起来让我觉得“不对劲”。

因此，请不要要求“过去的我”像产品经理或程序员一样给出专业规格。

你的任务是：

**把我后来通过很多轮开发、修改、返工、UI 调整、功能补充后才逐渐明确的需求，反向整理成一份普通用户也能在项目第一天说出来的高质量需求。**

# 六、反向生成「Day 1 初始需求提示词」

完成复盘后，请重新生成一份：

# 《如果今天重新从零开始开发这个项目，我应该第一次发给计划者的提示词》

这是整个任务最重要的产物。

## 1. 必须使用普通用户语言

我是编程小白。

## 2. 但必须足够具体

至少应该根据本项目真实情况明确：

- 为什么要做这个产品；
- 谁会使用；
- 是个人使用还是多人使用；
- 最常见的使用场景；
- 用户完整操作流程；
- 核心功能；
- 次要功能；

- 以后怎样查找；
- 怎样编辑；
- 怎样删除；
- 怎样分类；
- 怎样搜索；
- 是否需要筛选；
- 是否需要排序；
- 是否需要统计；
- 是否需要地图；
- 是否需要定位；
- 是否需要图片；
- 是否需要导入导出；
- 是否需要登录；
- 是否需要云同步；
- 是否考虑移动端；
- 是否考虑桌面端；
- UI 大概希望是什么感觉；
- 哪些操作必须足够简单；
- 哪些地方绝对不能复杂；
- 哪些功能可以以后再做。

只保留本项目真正相关的内容。

## 3. 尽量使用“真实使用故事”

不要只写：

> 需要搜索、分类、标签。

应该尽可能表达成：

> 当以后已经保存了几百条内容时，我希望能够直接通过关键词找到以前保存的内容，也能通过分类或标签快速缩小范围，而不是只能一条条往下翻。

通过真实使用场景帮助计划者理解需求产生的原因。

## 4. 明确产品边界

请明确：

### V1 必须完成什么？

哪些功能没有完成，就不能算这个产品已经具备基本可用状态？

同时明确：

### 哪些可以以后再做？

避免项目第一版无限膨胀。

## 5. 明确完成标准

不要使用：

> 界面好看。

这种无法验收的要求。

尽量转化成类似：

- 高频操作在尽量少的步骤内完成；
- 常用按钮容易找到；
- 页面信息不要过度拥挤；
- 不要求普通用户理解技术概念；
- 手机端主要功能能够正常操作；
- 数据保存后可以方便再次找到。

具体标准根据本项目真实情况制定。
