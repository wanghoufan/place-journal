# 个人打卡小工具：需求差距分析与改进指南

> 版本：V1.0（2026-09-05，第一阶段独立分析基线）  
> 角色：复盘分析师 + 产品需求老师 + Agent 协作顾问  
> 说明：本文研究“需求认知怎样逐步变清楚”，不是代码评分，也不是下一轮开发清单。第一阶段严格未读取同目录任何“Day 1 初始需求反推”材料及其他 Worker 输出。

## 1. 项目背景

这个项目原本是一个很生活化的想法：去到一个地方，拍照、说几句感受，以后能按地点、时间、标签回忆，还能把推荐分享给朋友。现在它叫“我的地点·私人打卡手账”，定位是手机优先、可安装的 PWA（可以像 App 一样安装的网页），本地优先保存并可同步云端。

这里最容易产生误会：一句“我想做个地点打卡工具”，实际上同时包含了记录、整理、查找、分享、隐私、跨设备、异常恢复等十几个小产品。最初的愿望并没有错；问题是愿望、规则和验收条件没有一开始分层写清楚，于是 Agent 只能在开发中不断补全。

证据基线：产品方案的目标与范围见 `docs/V1_PRODUCT_AND_TECHNICAL_PLAN.md` §0–§2；当前收工状态见 `docs/handoff/HANDOFF.md` §0；真实回归见 `docs/qa/QA回归报告丨Vercel上线丨2026-09-04.md`、`docs/qa/真机QA报告丨Vercel上线丨2026-09-04.md`。本文只据这些允许材料及 `src/` 当前实现、Git 历史分析。

## 2. 当前产品已经发展成什么样

当前不是“一个拍照页面”，而是一条完整链路：

`画廊回顾 → 记录照片/地点/语音或文字 → AI 整理 → 用户确认 → 记录详情编辑 → 按地点归档/标签查找 → 单地点或多地点分享 → 公开快照/地图`。

页面包括画廊、记录、AI 确认、记录详情、地点详情时间线、找地点、标签与维度、我的、单地点分享、多地点分享和地图总览。数据层包括照片缩略图/展示图、地点、到访记录、父子标签、分享快照、IndexedDB 本地库、outbox（待同步队列）和 Supabase `habit_tracker` Schema。

已被真实证据验证的能力包括：L2 云端写入回读、标签同步、AI/腾讯 ASR 真链路、Vercel HTTPS 手机录音、主题切换、分享图下载、删除确认与分享撤销、空地点清理、Find 评分筛选、demo 数据不再上云。仍有边界：高德 Key 联调、用户日常登录确认、跨设备/并发验收被取消或待验证；这些不是“页面有没有做”的问题，而是运行环境和验收范围问题。

## 3. 最开始与现在的差距：十个重要差距

下面每项都用同一套七问。 “最开始”指早期产品想法及方案中已经表达的用户愿望；不把后来的修复倒装成一开始就明确的要求。

### 差距 1：从“记下来”到“完整生命周期”

1. **当时怎么说**：我想拍照、说感受，AI 整理后保存成地点记录。
2. **现在什么样**：除了新增，还要查看、编辑评分/文字/封面、再次到访、删除记录、删除后清理分享和空地点。
3. **差在哪**：当时描述了“出生”，没有描述一条数据以后怎么被改、删、撤销和清理。
4. **为什么应提前想**：现实中一定会拍错、说错、改变推荐；这次真机 QA 发现删除无确认、删除后分享仍有效、空地点残留，后来又发现云端删除会被 pullRemote 拉回，说明生命周期不是小补丁。
5. **不说会怎样**：Agent 只做保存按钮；后面改数据结构、同步动作、分享级联，甚至会出现隐私风险。
6. **下次怎么说**：“每条记录都要能新增、查看、修改和删除。删除前要确认；如果它被分享，必须告诉我并让分享失效；地点没有记录时要自动清理或给删除入口。”
7. **好处**：一开始就能设计完整的保存、编辑、删除和回收路径，减少返工与数据复活。

### 差距 2：从“能录音”到“真实设备与失败降级”

1. **当时怎么说**：按住说话，语音转文字，再交给 AI。
2. **现在什么样**：手机 HTTPS 才能录音；HTTP 要明确提示；不支持、没权限、超短录音、空转写、未配置服务都要能手动填写。
3. **差在哪**：当时说了理想链路，没说设备、地址、权限和服务失败时怎么办。
4. **为什么应提前想**：桌面 localhost 与手机局域网的安全上下文不同；真机 QA 发现录音限制，后来才通过 Vercel HTTPS 解锁，并补了短按提示。
5. **不说会怎样**：开发完成后才发现“按钮点了没反应”，用户误以为产品坏了；测试还可能把环境限制误报成代码缺陷。
6. **下次怎么说**：“主要在手机使用。手机必须能按住录音；如果当前地址不能录音、没授权或没听清，要用人话提示并保留手动输入，不能卡死保存。”
7. **好处**：开发和验收会覆盖真机、HTTPS、权限、短按和降级，不会把理想环境当产品现实。

### 差距 3：从“有照片”到“照片数量、封面与容量规则”

1. **当时怎么说**：一次记录可以拍多张照片。
2. **现在什么样**：一条记录 1–9 张代表照，任意照片可设封面；图片压缩为展示图/缩略图，提示体积和 Storage 风险，原图不作为云盘备份。
3. **差在哪**：当时说了“多张”，没有说封面是谁、能否换、太多照片怎样处理、原图放哪里。
4. **为什么应提前想**：画廊必须知道显示哪一张；真实照片会很大，方案甚至用 353 张说明容量风险；后来封面切换才在真机发现缺入口。
5. **不说会怎样**：卡片封面规则反复改，上传可能卡死或耗尽免费空间，用户以为工具替他备份了原图。
6. **下次怎么说**：“一条到访记录通常放 1–9 张代表照，第一张默认封面但我能换；要压缩后保存展示图和缩略图，原图仍在手机相册，大量照片要提示容量并可恢复上传。”
7. **好处**：视觉、数据、上传队列和存储成本从第一天就一致。

### 差距 4：从“以后找得到”到“可计算的检索规则”

1. **当时怎么说**：以后按地点、标签、时间，或者说“海口适合拍照的地方”找回来。
2. **现在什么样**：Find 将自然语言解析为地区、预算、星级、活动、人群和标签条件；支持父标签包含子标签、标签交集、评分筛选和排序；搜索输入与标签筛选分开。
3. **差在哪**：当时说了“能找”，没有定义“找”的条件如何组合、父子标签是否包含、同名标签如何区分。
4. **为什么应提前想**：数据一多，搜索是核心价值；后来出现标签 chip 不能取消、子串误选（“咖啡”误亮“咖啡茶饮”）和评分筛选新增，都是规则未提前说完整的表现。
5. **不说会怎样**：Agent 会凭感觉做模糊搜索，用户看到结果却不信任；之后改查询、标签关系和 UI 交互。
6. **下次怎么说**：“我既要输入一句话，也要手动筛选。多个标签表示同时满足；选父标签要包含所有子标签；再次点已选条件要取消；评分按地点最高分筛选，并把搜索和筛选分开。”
7. **好处**：结果可解释、可验收，数据结构不会被错误的字符串匹配绑死。

### 差距 5：从“有标签”到“个人分类体系的管理权”

1. **当时怎么说**：希望有默认标签，也能按自己的方式分类地点。
2. **现在什么样**：标签按维度管理，普通维度最多父→子两层；记录存叶子标签，父级由关系推导；支持新增、改名、真删除、使用计数和父链同步。
3. **差在哪**：当时说“分类”，没有说层级上限、删除后的引用、同名标签和 AI 找不到标签时怎么办。
4. **为什么应提前想**：标签既是用户界面，也是查找数据；早期标签同步曾丢失，删除也一度只是 upsert 不真删，后续补了 `delete_tags` 和父链上云。
5. **不说会怎样**：删除按钮可能只删界面不删数据，刷新又回来；AI 可能擅自创建标签；不同维度同名导致筛选误亮。
6. **下次怎么说**：“标签由我管理，普通标签只允许两层；记录只记最具体的标签。删除标签要先清理它在记录中的使用；AI 只能推荐已有标签，找不到就让我选择是否新增。”
7. **好处**：分类长期可维护，筛选、同步和 AI 的责任边界清楚。

### 差距 6：从“分享给朋友”到“公开内容与撤销语义”

1. **当时怎么说**：可以分享一个地点或一份地点清单，拿到链接的人能看。
2. **现在什么样**：分享是字段白名单快照；可选公开理由、照片、标签和预算；默认不含私密感受、原始语音、完整历史、精确坐标；支持保存分享图、链接分享和撤销。
3. **差在哪**：当时表达了“分享对象”，没有逐项说哪些内容能公开、修改后是否跟着变、删记录是否联动失效。
4. **为什么应提前想**：分享会把私人数据送出产品边界；这次真机发现删记录后分享仍有效，后来才补级联撤销和匿名 RPC 验证。
5. **不说会怎样**：可能泄漏私密文字或原图，也可能出现用户以为删掉了但朋友链接仍可访问。
6. **下次怎么说**：“分享只公开我勾选的照片、地点名、区域、评分、预算、公开理由和少量标签；它是快照。撤销或删除来源记录后，链接必须打不开，并在操作前告诉我影响。”
7. **好处**：隐私验收有明确白名单，分享与删除不会互相打架。

### 差距 7：从“手机优先”到“各端真实边界”

1. **当时怎么说**：以手机为主，也希望电脑能用，并可安装 PWA。
2. **现在什么样**：响应式页面、手机 HTTPS 录音、桌面网页和 Docker/Vercel 三端部署；不同端的 Key、OAuth 白名单和构建期变量分别验证。
3. **差在哪**：当时说了优先级，没有说各端哪些能力必须一致、哪些能力受浏览器限制、怎样算通过。
4. **为什么应提前想**：8081 OAuth 白名单遗漏、HTTP 录音不可用、Vercel 函数 ESM 打包失败，均是“端不同”在上线后才暴露。
5. **不说会怎样**：本地通过却生产失败；桌面截图通过却手机关键链路失败。
6. **下次怎么说**：“手机是主验收端，电脑用于整理和管理；三端都要能记录、回顾、分享，但录音必须在 HTTPS 手机测，OAuth 和地图要按每个正式域名单独验。”
7. **好处**：验收矩阵从第一天就按设备和环境拆开，部署问题不会伪装成功。

### 差距 8：从“自动同步”到“保存成功、离线和冲突”

1. **当时怎么说**：本地优先，联网后自动同步，换设备不丢。
2. **现在什么样**：IndexedDB 先保存，outbox 排队上传，显示本机/同步中/已同步/失败；云端按记录写入并有 revision；L2 以写入回执和刷新回读证明，跨设备/并发 L3 后来取消。
3. **差在哪**：当时说了方向，没有说“什么时候算成功”、重复提交、删除、旧版本冲突和是否验收第二设备。
4. **为什么应提前想**：曾出现标签未上云、pullRemote 覆盖本地关系、删除记录被云端回拉复活；这些不是网络按钮的问题，而是同步规则。
5. **不说会怎样**：页面显示“已保存”但云端没有；刷新丢数据或旧数据复活；多端时静默覆盖。
6. **下次怎么说**：“先保证本地能保存；云端成功必须有明确回执，刷新后还读得到。断网要显示未同步，重试不能重复。删除也要同步；如果两处修改冲突，不要偷偷覆盖，要让我裁决。”
7. **好处**：用户知道数据到底在哪里，开发可按证据验收而不是看页面颜色。

### 差距 9：从“做得好看”到“可执行的界面与状态”

1. **当时怎么说**：想要暖色、私人旅行手账、照片第一的感觉。
2. **现在什么样**：暖纸/票根/竹青三主题、米白纸张和陶土橙；页面还定义空状态、加载、按钮三态、底部弹层和分享图。
3. **差在哪**：风格词不是交互规格；缺地点、缺内容、等待、失败、空数据时的状态也必须设计。
4. **为什么应提前想**：真机发现 AI 按钮“点不动”但没有说明缺什么；AI 超时、空评分、浏览器录音限制也需要文案。后来才补三态按钮和等待/降级提示。
5. **不说会怎样**：用户把合理禁用当成故障，验收人员把设计差异当 bug，视觉返工反复发生。
6. **下次怎么说**：“除了正常画面，请把第一次空库、正在处理、失败、没有地点、没有内容、没有评分和删除确认都画出来；按钮禁用时要直接说还缺什么。”
7. **好处**：界面不仅好看，也能教用户下一步怎么做，验收更一致。

### 差距 10：从“完成功能”到“完成验收”

1. **当时怎么说**：把页面和功能做出来，能用就行。
2. **现在什么样**：M0–M6 分阶段，并用静态、API、真登录、匿名分享、手机、刷新重读、删除级联等证据分别验收；报告明确 PASS/FAIL/BLOCKED。
3. **差在哪**：当时默认“开发完成”等于“产品完成”，没有为关键场景写通过条件。
4. **为什么应提前想**：一次 QA 报告有 8 个 FAIL，甄别后真问题仅 2 个；另一次“弹窗已修”其实是死代码，直到复测才发现。证据口径不清会掩盖问题。
5. **不说会怎样**：静态 build、HTTP 200、页面显示被误当作云端保存或用户体验通过；测试数据还会污染云端。
6. **下次怎么说**：“每个核心功能都写成我能判断的句子：我做什么、应该看到什么、刷新后是否还在、失败怎么办、在哪台设备测。报告把已通过、未测和环境阻塞分开。”
7. **好处**：问题更早暴露，责任可追踪，第二阶段能真正交叉验证而不是重复猜测。

## 4. 返工真正来自哪里

### A 类：沟通得更好本来可以避免

- 没有第一天写完整生命周期：删除确认、分享失效、空地点、单条删除与地点级联后补齐。
- 没有一开始定义检索规则：标签取消、整词匹配、交集、评分筛选逐步补齐。
- 没有先定义照片/分享边界：封面切换、分享字段白名单、原图不上传和容量提示在实现中才变得具体。
- 没有把“手机优先”写成设备/HTTPS/权限验收矩阵：局域网录音限制、8081 OAuth 白名单和 Vercel 配置事故后才显形。
- 没有把“云端保存成功”定义为回执+刷新回读，导致标签、demo、删除和拉回问题需要后续证据化修复。

### B 类：正常产品迭代，不应自责

- 看见真实页面后才发现按钮文案、卡片信息密度、主题细节和分享图间距不舒服。
- 真照片、真手机、真麦克风和真实网络才会暴露体验差异；这是原型无法完全替代的使用反馈。
- 评分筛选是用户在实际使用 Find 后提出的自然增强；它不是早期核心链路缺失。
- 三主题、分享长图和“微信拦截外链时保存图片”属于看到产品后形成的表达升级。

### C 类：Planner/Agent 本来应该主动发现

- 对一个“私人记录工具”，计划者应主动追问删除、编辑、撤销、误操作和空状态，而不是等用户报 bug。
- 对语音功能，计划者应主动问主设备、HTTPS、权限拒绝、无声和超时降级。
- 对“以后能找”，计划者应主动把父子标签、交集、取消、排序、同名和数据多后的体验变成规则。
- 对“自动同步”，计划者应主动给出保存成功定义、删除同步、重复幂等、冲突和数据清理方案。
- 对上线验收，计划者应主动区分静态检查、环境阻塞、真机验收、云端回读和测试数据隔离。

结论不是“用户说清楚就万事大吉”，也不是“Agent 自己全猜”。用户负责生活目标和取舍；Planner 负责把隐含风险问出来并写成可验收方案；Developer 负责技术实现和技术边界。

## 5. 用户、Planner、Developer 的职责边界

### 用户应负责说清楚

- 为什么做、谁用、主要在什么时候用，以及一次最常见的完整过程。
- 什么信息最重要，哪些内容私密，哪些内容可以分享。
- 手机/电脑优先级、速度与准确性的取舍、哪些操作绝对不能麻烦。
- 数据错了如何处理的偏好（例如宁可确认一次，也不要静默删除）。
- 关键范围取舍：首发做什么、不做什么；什么算“好用”。

### Planner 应主动追问与提醒

- 空库、加载、失败、无权限、网络断开、重复点击、误删和撤销。
- 数据从新增到编辑、删除、恢复、分享、同步的完整生命线。
- 真实设备、浏览器、账号、域名、密钥配置和验收证据。
- 需求之间的冲突：例如“自动整理”不能变成“未经确认自动改标签”。
- 哪些是 MVP，哪些是正常迭代，哪些需要用户做决定；并记录假设，不能把猜测写成事实。

### Developer 可自行决定

数据库表怎样拆、API 叫什么、React 如何分组件、状态管理和缓存怎么选、压缩算法和队列内部实现、目录命名、日志和测试工具等。前提是满足用户目标、隐私/安全边界、可维护性和验收条件。

### 一个简单判断法

如果问题是“我希望用户最后看到/做到什么”，用户要回答；如果问题是“用户没想到但失败时一定会遇到什么”，Planner 要追问；如果问题是“在已确定目标下怎样稳定实现”，Developer 自决。涉及费用、隐私、公开范围、数据删除和不可逆操作时，不能由 Developer 擅自决定。

## 6. 编程小白的 10 问表达框架

### 1）我为什么要做它？

**为什么**：目的决定功能优先级；“记录回忆”和“公开推荐”不是同一产品。  
**不说会怎样**：Agent 会堆地图、AI或社交功能，却忽略最常用的记录。  
**怎么说**：“我想把去过的地方和当时感受留下来，以后按自己的标准快速回忆和推荐，不想做公开点评社区。”

### 2）我什么时候、在哪台设备上用？

**为什么**：手机、电脑、HTTPS、权限和网络会改变体验。  
**不说会怎样**：桌面通过，手机录音失败；本地通过，正式域名登录失败。  
**怎么说**：“我到店时主要用手机，回家可用电脑整理；手机是真正的首发验收端。”

### 3）一次完整使用过程是什么？

**为什么**：能把页面顺序和中间状态说清楚。  
**不说会怎样**：页面都存在，却不知道从记录到保存如何连起来。  
**怎么说**：“我打开记录，选照片和地点，按住说话或手填，看到 AI 建议，改好后确认保存，再在详情里查看。”

### 4）我到底要保存什么？

**为什么**：照片、地点、一次到访、评分、预算和感受的关系不同。  
**不说会怎样**：同一地点多次到访可能被覆盖，或每张照片变成一条记录。  
**怎么说**：“一个地点可以有很多次到访；每次是一条记录，可有多张照片、日期、评分、预算、感受和标签。”

### 5）数据以后怎么改、删、撤销？

**为什么**：现实数据一定会错，分享还会影响隐私。  
**不说会怎样**：删除无确认、分享仍可访问、空地点或云端旧记录复活。  
**怎么说**：“我要能编辑和删除；删除前确认，删除已分享记录时要联动失效分享并告诉我。”

### 6）数据多以后我怎么找？

**为什么**：几百条记录时，首页滚动不再够用。  
**不说会怎样**：只能按字符串猜，父标签和组合条件结果不可信。  
**怎么说**：“我能输入‘海口适合拍照、100 元内’，也能手动选地区、场景、标签和评分；多个条件要同时满足，点一次已选条件能取消。”

### 7）哪些信息私密，哪些可以公开？

**为什么**：分享不是把私人记录整条复制出去。  
**不说会怎样**：原始语音、私密笔记、精确位置或 EXIF 可能泄露。  
**怎么说**：“分享只放我明确选择的照片和公开理由，私密感受、原始语音、完整历史和精确坐标默认不公开；链接可以撤销。”

### 8）网络不好或服务失败时怎么办？

**为什么**：AI、ASR、云同步和地图都可能失败。  
**不说会怎样**：用户以为没保存，或页面一直转圈。  
**怎么说**：“断网也能先保存本机；AI/语音失败就提示原因并让我手填；恢复网络后可重试，重复重试不能产生重复记录。”

### 9）我对自动化的底线是什么？

**为什么**：自动化越强，误改风险越大。  
**不说会怎样**：AI 擅自创建标签、改评分或直接写入正式记录。  
**怎么说**：“AI 可以帮我整理建议，但必须先让我确认；只能匹配已有标签，新增或删除都要我点确认。”

### 10）什么才算完成？

**为什么**：完成不是 build 通过，而是关键旅程有证据。  
**不说会怎样**：把 HTTP 200、截图或本地页面当成云端成功。  
**怎么说**：“请用测试数据验证手机记录、刷新回读、断网重试、分享匿名访问、撤销、删除联动，并把 PASS、待验证和环境阻塞分开写。”

## 8. 三个最终结论

### 结论 1：这次返工最主要的 3–5 个原因

第一，最初表达偏“愿望清单”，没有把数据生命周期、异常、删除和验收写成规则。第二，把“手机优先、自动同步、可以分享、以后能找”当成一句话，实际却分别涉及设备环境、数据一致性、隐私快照和检索逻辑。第三，Planner 没有在早期主动追问隐含边界，导致封面、标签父链、删除联动、评分筛选和失败降级在真实 QA 后才变具体。第四，静态实现、局部页面表现和真实运行证据没有一开始严格分层，曾出现死代码被误判已修、测试数据上云和删除复活等问题。

### 结论 2：只能改变一个习惯时，最值得改变什么？

最值得改变的是：**不要只描述“我要什么功能”，每个功能都补一句“我会怎样使用、出错时怎样、怎样算完成”。**

例如不要只说“我要分享”，而说“我勾选照片和公开理由生成快照，朋友无需登录能看；我撤销或删除原记录后链接打不开；刷新和匿名访问都要实测”。这一句话会同时改变页面、数据、隐私、异常和验收，收益远大于多列几个功能名。

### 结论 3：模糊想法出现时，先要求 Planner 做什么？

先要求 Planner **把模糊想法整理成一页“用户旅程 + 追问清单 + 范围边界 + 验收场景”**，并明确标出哪些是用户决定、哪些是 Planner 假设、哪些由技术自决。等这页得到确认，再做页面原型和技术方案，最后才写代码。
