## E-001｜要让智能体连续开发、别被小问题打断，就用「第二个选项」这种表达方式（2026-09-18）

### 1. 小白解释

你要的是：AI 接手后**一口气把活干完，中间别老来打断你**。

问题是——用户（尤其是不懂技术的）通常不知道该怎么把这句话说出来，只能被动等 AI 一个个小问题来问、一次次停下来等你回答。

正确的表达方式其实很简单：**直接引用选项的原文——「按第 2 个选项来」**。

为什么这样说管用？因为第 2 项的原文已经把话说全了：「MVP Gate 只做内部检查点、不暂停、连续完成 `T086–T120`，最后只请人验收完整 V1 Gate」。引用编号＝引用这段完整定义，AI 没有猜的空间，也就没有理由再来问你。而自己缩写成「连续开发」四个字，定义就丢了，AI 只能反问或者乱猜——于是又变成打断你。

一句话：**想不被打断，就用选项原文把话说全，别用自造简称。**

### 2. 问题 / 现象

用户想要「连续开发、不要中断」，但**不知道该怎么表述**，于是只能被动应对 AI 抛来的一个个小问题（例如 HD-01 这种二选一），被反复打断。

正确做法：下达时明确用**交付切片第 2 个选项（B｜连续开发）**这种表达方式。

### 3. 为什么是问题

- **简称丢了定义**：「连续开发」四个字不带任何边界信息——中间停不停？检查点谁记？最后验收哪个 Gate？全靠猜。
- **猜不出来就来回问**：AI 无法确定节奏，只能反问确认，于是每一次都变成一次打断。用户越是不懂技术，越答不上来，越容易被卡住。
- **歧义代价高**：中文「连续开发」字面可读成「不间断写代码」「持续迭代开发」等；AI 若按字面理解，可能中途完全不设检查点，也可能反过来频繁停顿汇报，两种都偏离原意。
- **打断的还多是小事**：节奏、口径这类问题本该由执行方自己定，却因为表述不清被抬成「要用户拍板的问题」，白白消耗小白用户的注意力和耐心。

### 4. 原因 / 背景（核对结果）

- `docs/pm/PRODUCT_PLAN_V1.0.md:224`（HD-01｜交付切片二选一）原文已把两项定义写全，第 2 项为：
  > **B｜连续开发**：`T001–T085` 通过 MVP Gate 后只由 TM 记录内部检查点，不暂停，连续完成 `T086–T120`，最终只请人验收完整 V1 Gate。
- 同条注明「两项都保留相同的 MVP Gate 与完整 V1 Gate、相同 T001–T120 总范围和最终 DoD；差别仅是 MVP PASS 后是否停下来请人拍板」——**权威表述已经存在，且是完整的**，直接引用即可，不需要另造词。
- `docs/handoff/HANDOFF.md:25` 同项登记为「HD-01 交付切片二选一（A 分段停靠建议／B 连续开发）」。
- 归因：不是 AI 猜不出，是下达时**放弃了已有的权威表述、改用自造简称**；也不是用户不会提要求，是**没人告诉他可以这样提**。

### 5. 本次纠正

用户明确：

1. **后面如果说要让智能体连续开发，应该用「第二个选项」这种表达方式。**
2. 用户是小白，以前不知道怎么表述；**诉求是「别老是打断我、别老因为小问题来问我、不要中途断开」。**
3. 本次交付切片用户已拍板选 **B（连续开发）**。

### 6. 以后怎么避免

- 下达节奏／切片类指令时，**引用选项编号或选项原文**（「按第 2 个选项」「按 B｜连续开发」），不用自造简称。
- 一组选项已经在计划文档里定义过，就直接引它；引用前确认该选项仍在文档里、文字未变。
- **给小白用户提供可直接复制的一句话派单话术**（见第 7 段），不要求他自己组织技术表述。
- 执行方侧配套：**口径类／节奏类小问题自己定、写进文档，不要中断用户**；只有资源、授权、费用、真机、密钥这类必须用户拍板的事才找人，并且**攒起来一次问**，不要一件一问。

### 7. 下次可以直接对 Agent 说的话

> 交付切片按第 2 个选项（B｜连续开发）来：MVP Gate 只做内部检查点、不暂停，一口气做完全部任务再一起验收。中途不要为小问题打断我，口径和节奏你自己定、写进文档；只有账号、授权、费用、真机这类必须我拍板的事才找我，而且攒起来一次问。

### 8. 技术处理（只描述，不执行）

- 派单话术／交接里，节奏指令建议写成：`交付切片＝选项 2（B｜连续开发）`，必要时附选项原文一句。
- 派单话术建议加一段「不打断约定」：口径类自行决定并落文档；必问项攒批，一次问完。
- 交付切片拍板结论（= B）的落盘位置属 ORCA 会话职责范围；本文件只作经验登记，不代办。

### 9. 适用范围

- 所有用「多选项交付切片」派活的项目（SDD／ORCA 类计划）。
- 尤其适用于**不懂技术、用语音下达指令的用户**：他们不会主动组织精确表述，需要现成话术。
- 可升级为**通用项目模板经验**：有权威原文时引用原文，不自造简称；简称等于丢定义，丢定义等于换来一次次打断。

## E-002｜修完默认推送并部署到 Vercel、自行线上验证、真机实测，不让用户追着问（2026-09-20，2026-09-20 追令补写）

### 1. 小白解释

你要的是：修完 Bug 就**一口气推上去、发到线上、自己打开网站和手机验一遍，确认真好了再来告诉你**，而不是修完就停下、等你追问才动手。

### 2. 问题 / 现象

修完代码后停在本地，不主动推、不发 Vercel、不打开线上验证，需要用户反复追问才继续；且未做真机与实际网站测试就报完成。

### 3. 为什么是问题

- 用户要的是结果（线上能用），本地改完不等于线上好了。
- 每停一次就要用户追一次，消耗注意力；问题若在线上仍复现，还要再返工一轮。
- 不做真机＋真站验证就报完成，等于把验收成本转嫁给用户。

### 4. 原因 / 背景（核对结果）

- 用户亲令（2026-09-20）：修完默认推＋发 Vercel，不让用户追；自己去线上测刚改的功能是否生效；有问题继续改到解决为止；务必真机测试＋实际网站测试。
- 用户追令（2026-09-20）：真机测试与网站实测走 computer use 直接操作；谷歌浏览器里已有登录好的账号，直接用，效果更好。
- 本项目已有对应能力与约定：`scripts/deploy.sh` 规范部署、Vercel 生产站、真机 QA 流程（见 AGENTS.md）；缺的是把这四步当作默认收尾动作。
- 原话含情绪化表达，登记时已转书面语，语义不变。

### 5. 本次纠正

用户明确修完后的默认四步：1) 默认推（按项目 git 规范走）；2) 发 Vercel；3) 自己去线上测刚改功能是否生效，有问题继续改到解决为止；4) 务必真机测试＋实际网站测试，真机与网站实测走 computer use 直接操作。不让用户追着问进度。网站实测优先用谷歌浏览器里已登录好的账号直接测，不另起账号、不重复登录。

### 6. 以后怎么避免

- 修 Bug／改功能默认带上「推＋发＋线上验＋真机验」四步收尾，做完再报完成；报完成时附线上验证结论（通过／不通过＋证据）。
- 真机测试与网站实测默认走 computer use 直接操作，不只看日志或截图推断。
- 网站实测优先复用谷歌浏览器里已登录好的账号直接测，不另起账号、不要求用户重新给账号密码；若已登录态失效才找用户，并且攒起来一次问。
- 线上验证不通过则继续改到解决为止，不把半成品交回给用户。
- 若当次确有原因不能推或不能发（如用户另有指令、密钥缺失），在收工时主动说明原因和下一步，不等用户追问。

### 7. 下次可以直接对 Agent 说的话

> 修完默认推＋发 Vercel，不用我追；自己去线上测刚改的功能是否生效，有问题继续改到解决为止；务必做真机测试＋实际网站测试，真机与网站实测走 computer use 直接操作；谷歌浏览器里已有登录好的账号，直接用，验完再报完成。

### 8. 技术处理（只描述，不执行）

- 收尾顺序建议：本地验证 → 推（遵守未确认禁 commit/push 等项目硬守则，有冲突时先请示）→ 发 Vercel（`scripts/deploy.sh` 或项目既定通道）→ 线上实际网站验证刚改功能（走 computer use 直接操作，优先复用谷歌浏览器已登录账号） → 真机验证（走 computer use 直接操作）→ 回报结论与证据。
- 线上验证结论建议落 HANDOFF 或 QA 记录；本文件只作经验登记，不代办。

### 9. 适用范围

- 本项目所有修 Bug／改功能任务；可推广为各项目默认收尾约定（有特殊发布流程的项目以其流程为准，但「自行线上验证＋真机验证再报完成」不变）。

## E-003｜地点改名回退根因＝推送回写窗口并发覆盖，根治用 writeBackIfUnchanged＋saveTags revision+1（2026-09-20）

### 1. 小白解释

地点改完名字又变回去，不是因为没保存，而是保存过程中被另一份旧数据盖掉了。

### 2. 问题 / 现象

地点改名后短暂生效，随后自动回退为旧名。

### 3. 为什么是问题

用户以为改名失败会反复重试，重试仍被覆盖；且回退与正常保存难以区分，易误判为同步丢失。

### 4. 原因 / 背景（含核对结果）

根因为推送回写窗口并发覆盖：读快照 → 网络等待 → 回写，窗口内旧快照覆盖新改名。

### 5. 本次纠正

根治方案定为 writeBackIfUnchanged 条件回写＋saveTags revision+1。

### 6. 以后怎么避免

涉及改名／标签回写的推送，一律走条件回写＋revision 递增；禁止无条件整行回写覆盖。

### 7. 下次可直接对 Agent 说的话

> 地点改名回写用 writeBackIfUnchanged＋saveTags revision+1，防止推送窗口并发覆盖导致回退。

### 8. 技术处理（只描述，不执行）

回写前比对 revision 未变才写；saveTags 成功后 revision+1；冲突走重试或提示，不静默覆盖。

### 9. 适用范围

本项目地点改名／标签回写；可推广到一切读快照→网络→回写路径。

## E-004｜线上双写误会：多端同改互盖先问是否多端同改，再查回退（2026-09-20）

### 1. 小白解释

两台手机同时改同一个地点名字，后保存的会盖掉先保存的，看起来像被系统改回去，其实是自己盖了自己。

### 2. 问题 / 现象

用户手机并发改名互盖，被误认为系统回退（E-003 类故障）。

### 3. 为什么是问题

误判会导向错误修复方向（改同步引擎），浪费排查成本；真相只是多端同时改了同一个字段。

### 4. 原因 / 背景（含核对结果）

用户多端同时改名，后写覆盖先写；现象与回退 Bug 外观一致，但根因不同。

### 5. 本次纠正

排查顺序定为：先问是否多端同改，再按 E-003 查回退。

### 6. 以后怎么避免

凡报“改名被改回去／线上数据对不上”，先问一句是否多端同改、改了同一地点／标签，再进技术排查。

### 7. 下次可直接对 Agent 说的话

> 报改名回退先问我是否多端同改，排除双写互盖后再查同步回写问题。

### 8. 技术处理（只描述，不执行）

排查先确认设备数、时间线、是否同字段并发写；确认双写则按冲突处理，不动同步引擎。

### 9. 适用范围

本项目所有改名／标签／地点字段异常排查；可推广为多端同步类问题通用首问。
