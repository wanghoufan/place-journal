### 【L2 阻塞根因】Supabase Auth 回调回落到 192.168.31.60:3100
- 现象：Google 登录全程无报错，但 5173 应用始终「已配置 · 未登录」；浏览器最终停在
  `http://192.168.31.60:3100/#access_token=…`（那是用户的提示词管理器）。
- 证据链（`agent-browser network requests --filter supabase`）：
  1. `GET /auth/v1/authorize?provider=google&redirect_to=http%3A%2F%2Flocalhost%3A5173`
  2. `GET /auth/v1/callback?state=…&code=…`
  3. 最终落地 `192.168.31.60:3100` ← **与 redirect_to 不一致**
- 结论：该项目 Auth 的 **Redirect URLs 白名单里没有 `http://localhost:5173`**，
  Supabase 静默忽略 `redirect_to`、回落到 Site URL。
  Site URL 被同项目下的提示词管理器（192.168.31.60:3100）占着 —— 这是共享 Supabase 项目的典型冲突。
- 性质：**配置问题，不是代码问题**。修复需进 Dashboard 加白名单，属本次验收禁止项。
- 另注：坑 2 已解决 —— Google 拦 Chrome for Testing，换真实 Chrome + CDP(9334) 后
  `navigator.webdriver=false`、可正常登录。
- 另注：`osascript activate "Google Chrome"` 在多 Chrome 实例下会带错窗口，
  导致用户在别的窗口登录（票据落在 3100）。必须用 CDP `/json/activate/<targetId>` 精确激活。
